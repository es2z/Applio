# リアルタイム変換: 遅延と音質の実験的オプション

Realtime タブ > Performance Settings > **遅延・音質の実験的オプション（初期値 = 従来の動作）**
（`rvc/realtime/options.py` の `RealtimeOptions`）。

- **すべてオプトイン**で、初期値は従来の動作そのものです。全オプションが初期値のとき、
  出力は変更前の main と**ビット単位で同一**です（CPU 上の APEX-GAN による
  エンドツーエンド比較で確認。`tests/test_realtime_options.py` の各テストも初期値の
  レイアウト・遅延が従来どおりであることを固定しています）。
- オプションは **Start 時に適用**されます。変えたら Stop → Start。
- **テンプレートに保存**されます（YAML の `experimentTab`）。オプション導入前に保存した
  テンプレートを読み込むと、全オプションが初期値（= 従来動作）になります。
- Start 後のステータスに `Options: <初期値から変えた項目>` と
  `window delay <ms>`（変換ウィンドウ自体が生む遅延）が出ます。
- 入力のハイパス（レポートの IO1）は、ノイズ除去済みで音色が変わる懸念があるため
  **実装していません**。

## 遅延の内訳（Chunk 960 ms で 2 秒を超えていた理由）

基準テンプレート（Chunk 960 ms / Crossfade 0.138 s / Extra 0.22 s）での内訳です。
「ウィンドウ遅延」はデバイスも処理時間も含まない、窓の配置だけで決まる遅延で、
変換を恒等写像に置き換えたシミュレーションで実測した値です
（`tests/test_realtime_options.py`）。

| | 従来 | 出力位置 trim | trim + ring 転送 |
|---|---|---|---|
| ブロックを集める | 960 | 960 | 960 |
| ウィンドウ遅延 | **370** | **150** | 150 |
| 出力側の待ち | **約 960**（1 チャンク） | 約 960 | **処理時間 p95 + 10 ms 程度** |
| デバイス | 数 ms〜数十 ms | 同左 | 同左 |
| 合計（目安） | 約 2.3 s | 約 2.1 s | 約 1.2 s |

- ウィンドウ遅延 370 ms = Extra 220 + Crossfade 138 + SOLA 10（を 10 ms 単位に丸め）。
  従来の配置は変換ウィンドウの**最も古い部分**を再生するため、Extra が「先読み」として
  そのまま遅延に乗っていました。trim では最新の部分を再生し、Extra は過去の文脈になる
  ので 150 ms（= Crossfade + SOLA を丸めたもの）になります。Extra を 1.0 s にすると
  従来は 1150 ms、trim は 150 ms のまま（実測）。
- 出力側の約 1 チャンクは、従来の転送（`rvc/realtime/audio.py`）がデバイスを
  blocksize = Chunk で開き、コールバック内で変換するためです。変換したブロックは
  「次に再生するバッファ」として渡されるので、もう 1 チャンク待ちます。WDM-KS 出力を
  使っていたのはこの一部を隠すためでした。ring 転送（段階 2）はこれを処理時間程度まで縮めます。

※ ring 転送の行は、シミュレーション（`tests/test_realtime_ring_transport.py`）で
「チャンク + 処理時間 + 予備 10 ms」になることを確認した値です。実機では
ステータスの `est. total` を見てください。

## 段階 1: 窓の配置・入力・ゲイン・APEX-GAN ノイズ

### 出力位置（`output_position`: legacy / trim）と先読み（`lookahead_s`）

- **legacy**: 従来どおり。再生する部分は約 370 ms（Extra 220 + Crossfade 138 + SOLA 10）先の音声まで参照できます。
- **trim**: 変換ウィンドウの最新の「ブロック + Crossfade + SOLA + 先読み」だけを生成して
  再生します（RVC WebUI と同じ配置。flow の端の影響を避けるため 24 フレームの余白を
  付けて生成）。Extra は過去の文脈になり、遅延に加算されなくなります。
- **音への影響**: 再生する部分が参照できる「未来」の音声は、trim では Crossfade + SOLA（10 ms）+ 先読み
  だけになります（HuBERT と RMVPE は前後両方の文脈を使います）。最新端の子音や
  音の立ち上がりで差が出る可能性があります。その場合は **先読み** を 0.05〜0.1 s
  にして聴き比べてください（1:1 で遅延が増えます）。trim のときだけ有効です。
- 付随する変更（trim のときのみ）: Index のブレンド範囲を生成に使う全フレームに合わせ、
  RMS ミックス（`volume_envelope`）の参照区間を生成区間に合わせています。legacy では
  従来のまま（従来は再生しない区間にだけ Index をブレンドしていました）。

### 入力の 48 kHz → 16 kHz 変換（`input_resample`: stateless / stateful）

- **stateless**: 従来どおり、ブロックごとに単独でリサンプル。ブロック境界ごとに
  フィルタの端の不連続が入ります（境界で 1e-2 以上の誤差、実測）。
- **stateful**: 1 本の連続した信号としてリサンプル（全体を一括でリサンプルしたものを
  24 サンプル = 0.5 ms 遅らせたものと 1e-5 以内で一致、実測）。
- FCN 系の F0 手法は自前の連続リサンプラを持つため対象外です。ブロックが 3 の倍数
  サンプルでない場合も従来の方式になります（ログに出ます）。

### Protect が使う有声判定（`protect_voicing`: f0 / unfilled）

- gaps-filled 系の F0 手法（`hpa-rmvpe-112000-aligned-filled` など）では全フレームが
  有声になるため、**従来は Protect が何もしていません**（穴埋めの意図どおりの動作）。
- **unfilled** にすると、穴埋め前の推定器の有声判定で Protect が働きます。子音や息の
  部分の特徴量が元の声側へブレンドされます。
- **Protect が 0.5 のときは何も変わりません**（Protect は 0.5 未満でのみ働く）。
  Protect を 0.5 未満にして使うときだけ意味があります。元の声の成分が子音に残る方向の
  変化なので、好みで判断してください。

### 出力ゲイン（`gain_mode`: legacy / aligned）

- この fork はリアルタイム出力に入力の sqrt(RMS) を掛けています。
- **legacy**: 最新の入力ブロック（+ Crossfade）から求めたゲインを、ブロックごとに 1 つ、
  ウィンドウ遅延ぶん古い音声に掛けます（ゲインの時刻がずれている）。
- **aligned**: 同じ sqrt(RMS) を、掛ける位置を中心に同じ長さで測り、10 ms ごとに
  滑らかに変化させます。定常的な入力では legacy と同じ音量になります（5% 以内、実測）。
  音量の時間的な追従が変わるので、語頭・語尾の音量感を聴き比べてください。

### APEX-GAN のノイズ包絡（`apex_noise_envelope`: window / fixed）と学習データの有声率

- APEX-GAN はノイズ包絡（有声 0.003 / 無声 0.033）を**バッチ全体の平均で割って**
  正規化します（学習時の実装をそのまま移植）。学習バッチは有声・無声が混ざるので
  平均は大きめになります。
- リアルタイムではウィンドウ 1 つが「バッチ」で、gaps-filled の F0 では**ウィンドウ全体が
  有声**になるため、平均が小さくなり、有声部のノイズが**学習時の 3〜6 倍**
  （有声率 0.8〜0.5 の場合）で入っています。これが **window**（従来どおり）です。
- **fixed**: 「学習データの有声率」を持つバッチで得られる平均（固定値）で割ります。
  学習時と同じノイズ量に戻す設定です。固定値は Start 時にログに出ます。
- 有声率は `env\python.exe -X utf8 tools\apex_noise_voiced_ratio.py <モデル名>` で
  学習フォルダ（`logs/<モデル名>`）から計算できます（学習で使う F0 = 穴埋め前の
  aligned F0 から、学習と同じ 36 フレームの窓で計算）。初期値 0.65。
- 今まで聴いてきた音は window の方です。fixed は「学習時と同じ」ですが、聴感上
  良くなるかは未確認です。必ず A/B してください。APEX-GAN 以外のモデルでは無視されます。

## 段階 2: ring 転送（WASAPI → WASAPI の遅延減少）とドリフト補正

### オーディオ転送方式（`transport`: legacy / ring）

`rvc/realtime/ring_transport.py`。破棄した `new_main_testversion`（29eae3d）の転送層を
移植し、出力予備の制御を書き直したものです。

- デバイスは小さいバッファ（blocksize 0 / latency "low"）で開き、コールバックは
  リングバッファへのコピーだけを行います。変換は専用スレッドで、ブロックが揃った
  瞬間に実行し、出力リングへ書きます。
- 出力リングに残す量（予備）は「処理時間の p95 + 10 ms」を目標にします。開始前に
  5 ブロックの処理時間を測り（RNG を消費しない形で）、最初のブロックの前にだけ
  必要な無音を入れます。アンダーフローが起きたら予備を 10 ms 増やし（2 秒に 1 回まで）、
  5 秒起きず 1 秒静かなら 10 ms 戻します。
- **変換に渡るものは従来と同じ**です（Chunk Size ぶんの 48 kHz モノラル、入力ゲイン適用、
  チャンネル数も従来と同じ開き方）。音が変わり得るのは次の 2 点だけです。
  - 予備のずれの補正: **-60 dBFS 未満の静かな出力ブロックだけ**、その中で最も静かな
    区間を短いクロスフェードで切り取る／繰り返す。声には触れません。
  - separate のときの可変レート・リサンプラ（下記）: 21 kHz まで平坦、22 kHz で -0.4 dB。
- ステータス行: 経路（`ring duplex/...` か `ring separate/... -> ...`）、処理時間 p50/p95、
  予備と出力リングの量、ウィンドウ遅延、デバイス遅延、**推定の総遅延（est. total）**、
  入出力の xrun 数、静音補正の回数、（separate のとき）ドリフト補正量。
- コールバックが数 ms ごとに GIL を取れるよう、ring 使用中は Python のスレッド切替間隔を
  1 ms にしています（停止時に戻します）。

### ring のストリーム（`ring_stream_mode`: auto / separate）

- **auto**: 入出力が同じホスト API なら全二重ストリーム 1 本（失敗したら 2 本に
  フォールバック）。1 本なら入出力は同じクロックで動くのでドリフト補正は不要です。
- **separate**: 常にストリーム 2 本。入力と出力が**別の機器**（クロックが別）なら
  こちらが安全です。出力リングの量から**ドリフト補正**（出力のリサンプル比を
  ±1000 ppm 以内で PI 制御、1000 ppm でも 1.7 セント）を行い、2 つのクロックの差を
  吸収します。シミュレーションで入力 +200 ppm を -200 ppm 前後に収束させ、
  アンダーフローなしを確認しています。
- 排他モードが拒否されたら共有モードで開き直し、ステータスに表示します。

### 使い方の目安

- まず auto で開始し、ステータスの `xruns in/out` が増え続けないか見てください。
  増える場合は separate、排他モードの切り替え、Chunk を変えて試してください。
- 入力と出力が別のオーディオ機器なら separate を推奨します（auto でも 2 機器を
  全二重 1 本で開けることはありますが、その場合 2 つのクロックの差は補正されません）。

## 段階 3: 乱数・位相・F0 を時刻に固定

`rvc/realtime/synthesis.py` と `rvc/realtime/pipeline.py`。どれも **Chunk Size が 40 ms の
倍数**（10 ms フレームの整数倍、かつ 48 kHz で 128 サンプルの倍数）のときだけ有効で、
そうでなければログに出して無効になります。960 ms は対象です。

従来は毎ブロック、変換ウィンドウ全体を作り直し、乱数も引き直し、正弦波の位相も 0 から
始めます。隣り合うブロックは同じ時刻の音を別々に生成し、クロスフェードでつないで
いるので、重なり部分で波形が一致しません。

- **ノイズを時刻に固定**（`time_locked_noise`）: flow の潜在ノイズと APEX-GAN の
  ノイズを、時刻に結び付いたバッファから取ります。ブロックごとに 1 ブロックぶん
  ずらし、新しい部分だけ引きます。RNG シード設定と併用すると再現性もあります。
- **正弦波の位相を連続させる**（`phase_continuity`、APEX-GAN のみ）: 励起の正弦波の
  位相を、前のブロックの生成区間の先頭から 1 ブロックぶん進めた値から始めます
  （float64 で累積し、2 つの窓が同じサンプルに達するよう量子化）。
- **F0 キャッシュ**（`f0_cache`）と **マージン**（`f0_cache_margin_ms`）:
  「1 ブロック + マージン」より古いフレームの F0 は推定し直さず保持します。
  マージンを先読み以下にすると、クロスフェード部分の F0 がそれを生成する 2 つの
  ブロックで同じになります。大きくすると F0 がより先の音声を見られる代わりに、
  クロスフェード部分で変わり得ます（初期値 100 ms）。
  - 保持された F0 は「そのフレームが最新側にあったとき」に、マージンぶんの未来しか
    見ずに推定した値です。出力位置 legacy では再生部分が窓の最も古い部分なので、
    従来は約 370 ms（Extra + Crossfade + SOLA）の未来を見て推定していた F0 が、マージンぶんだけの
    推定に置き換わります。**F0 キャッシュは trim と組み合わせる**前提です。
  - gaps-filled 系の F0 手法では、穴埋めもその時点の値で固定されます。マージンより
    長い無声区間は、後から来る有声フレームとの補間ではなく、直前の値の保持になります。

測定: 同じ時刻を重ねて生成した 2 つの窓の、重なり部分の相対誤差は、ノイズと位相を
固定すると **0.0019**、固定しないと **1.28**（APEX-GAN デコーダ単体、
`tests/test_realtime_synthesis.py`）。残る 0.0019 の大半はウィンドウ平均によるノイズ包絡の
差で、APEX-GAN のノイズ包絡を **fixed** にすると **0.00037** まで下がります。
そのため **時刻固定は fixed と組み合わせる**ことを勧めます。

音への影響は「つなぎ目のゆらぎ・うなり・音色の揺れが減る」方向を期待していますが、
ノイズの性質（ブロックごとの独立性）が変わるので、必ず A/B してください。

## 段階 4: 入出力の処理（IO1・IO4・IO5）と潜在ノイズの温度（P1）

どれも初期値は従来の動作です。IO3 は段階 1 の「入力の 48 kHz → 16 kHz 変換」
（`input_resample`）がそれに当たります。

### 入力のハイパス（`input_highpass_hz`、IO1）

- 0 = オフ。48 にすると、学習時の前処理の「Noise filter」と同じフィルタ
  （5 次バターワースのハイパス、48 kHz で設計、`rvc/train/preprocess/preprocess.py`）を、
  入力に 1 本の連続したストリームとしてかけます（全体に一括でかけた結果と 1e-5 以内で
  一致、実測）。
- 学習時と一致するのは、データセットを Noise filter 付きで前処理した場合だけです。
  付けずに前処理したモデルでは、学習時に無かった処理を足すことになります。
- 外部でノイズ除去をしている場合も、低域のゴロゴロ（机の振動、吹かれ）は残ることが
  あります。その場合に 48〜80 Hz で聴き比べる用途です。

### 出力をクリップする位置（`clip_stage`、IO4）

- **generator**（従来どおり）: 生成器の出力を、入力音量によるゲイン（sqrt(入力 RMS)）を
  かける**前に** ±1 で切り落とします。生成器が 1 を超えた部分はここで平らになり、
  そのあとゲインで小さくなるので、Applio の後ろのリミッタでは元に戻せません。
- **output**: 生成器の出力は切らず、ゲインをかけた後の最終出力だけを ±1 で切ります。
  ゲインはほぼ必ず 1 未満なので、実際には切られなくなります。
- 生成器が 1 を超えているかは、下の「レベル表示」で確認できます。超えていなければ
  どちらでも音は同じです。
- Applio 内のリミッタ・ディエッサは**実装していません**。pedalboard の Limiter は
  しきい値より小さい音でもゲインを上げて圧縮する（実測: しきい値 -1 dB で -20 dBFS の
  正弦波が +4.8 dB）ため安全策として使えず、外部の VST の方が高機能だからです。

### 無音ゲートのフェード（`gate_fade_ms`）と保持（`gate_hold`）（IO5）

- **gate_fade_ms**: 0 = オフ。無音ゲートが閉じるとき、従来は最後に変換した音から
  そのまま 0 に切り替わります。0 より大きいと、続くはずだった音（クロスフェード用に
  取ってある部分）をこの長さで cos² のフェードアウトにします。その音は使い切るので、
  再開時は無音からフェードインします。20〜50 ms が目安です。
- **gate_hold**: オフ（従来どおり）では、無音中にバッファを消去するとき無音ブロックの
  数え直しも行うため、**一定の部屋の雑音が続くと、ゲートが数ブロックごとに開いて
  変換した雑音が短く出る**ことを確認しました（240 ms ブロック、Silence Threshold
  -40 dB のシミュレーションで、閉じる 3 ブロック・開く 3 ブロックの繰り返し）。
  オンにすると、入力が無音でなくなるまでゲートを閉じたままにします。

### 潜在ノイズの温度（`latent_noise_scale`、P1）

- flow に入れる潜在ノイズの倍率です。従来は `Synthesizer.infer` の 0.66666 固定で、
  スライダーの 0.67 はこの従来値として扱います。
- 下げると、ざらつきや息っぽさが減って安定する代わりに、平板に聞こえることがあります。
  0.67 / 0.5 / 0.33 / 0 を、RNG シードを固定して聴き比べてください。
- 生成器の呼び出し方が変わるだけで、学習・モデル・処理時間には影響しません。

### レベル表示（常に表示、音は変えない）

ステータスに次の行が出ます（直近約 3 秒の最大と、開始からの最大）。

```
Level: generator peak -6.2 dBFS (max -3.1, 0 blocks over 0 dBFS) | output peak -18.4 dBFS (max -14.0)
```

- generator peak: 生成器の出力そのもの（クリップ前）。0 dBFS を超えたブロック数も出ます。
- output peak: Applio が出す音（Output Gain スライダーをかける前）。Applio の後ろに
  置いたリミッタが働くかどうかは、この値とリミッタのしきい値・入力ゲインで決まります。

### 実装しなかったもの: IO2（ノイズ抑制）

- 入力のノイズ除去はすでに外部で行っているので、Applio 内で重ねると子音が削れやすく
  なります（二重のノイズ除去は明瞭さを落とす典型的な原因です）。
- 候補だった DeepFilterNet3 は、必要な `deepfilterlib` に Python 3.13 用の
  ビルド済みパッケージが無く（`pip download` で確認するとソース配布だけで、Rust で
  ビルドが必要）、手元に入っている noisereduce のスペクトルゲートは、外部の
  ノイズ除去より品質が劣ります。

## A/B の手順

### 1. オフライン（デバイスなし、同じ録音で比較）

`tools/realtime_stream_eval.py` は Realtime タブと同じ VoiceChanger・ウォームアップ・
RNG シードで、録音をブロックごとに流して WAV と数値を書き出します。

```
env\python.exe -X utf8 tools\realtime_stream_eval.py --template <テンプレート名> ^
    --input voice.wav --preset legacy --preset trim --preset stage1 --offline
```

- 組み込みプリセット: `legacy`（全オプション初期値）、`template`（テンプレートに保存した
  オプション）、`trim`、`stage1`（trim + stateful + aligned）、`locked`
  （stage1 + ノイズ fixed + 時刻固定 3 種）。
- 任意の組み合わせ: `--preset "fixed065={\"output_position\": \"trim\", \"apex_noise_envelope\": \"fixed\", \"apex_noise_voiced_ratio\": 0.65}"`
  （`chunk_ms` / `crossfade_s` / `extra_s` も上書き可）。プリセットは完全な設定で、
  書いていないオプションは初期値です。
- 出力: `logs/stream_eval/<日時>/<入力名>__<プリセット名>.wav` と `results.json`。
  - `delay_ms`: ウィンドウ遅延。`p50_ms` / `p95_ms`: 1 ブロックの処理時間。
  - `seam`: つなぎ目の前後でのスペクトル変化 ÷ それ以外での変化。1.0 ならつなぎ目が
    区別できない。高いほどつなぎ目が目立つ。**どこを聴くかの目安**です。
  - `mel_vs_offline`（`--offline` 指定時）: 同じ録音を一括変換したものとの log-mel 距離。
    ストリーミングそのものによる劣化の目安です。
- 音色は数値ではなく耳で決めてください。数値は「差がどこにあるか」の手がかりです。

### 2. 実機

- オプションを変えて Stop → Start。比較したい組み合わせをそれぞれテンプレートに
  保存しておくと切り替えが楽です。
- 同じ入力で比べるには、録音を仮想ケーブル（VB-Cable など）経由で入力デバイスに
  流すのが確実です。
- **RNG シード**を固定すると、乱数による差を除いて比べられます。

### 進め方の例

1. legacy と trim（先読み 0 / 0.05 / 0.1）
2. + 入力 stateful
3. + ゲイン aligned
4. APEX-GAN ノイズ window と fixed（有声率はツールで計算した値）
5. Protect を 0.5 未満で使う場合だけ、f0 と unfilled
6. 転送を ring（auto → 必要なら separate）
7. ノイズ fixed の上で、時刻固定 3 種（まとめて → 1 つずつ外す）

## ファイル

- `rvc/realtime/options.py`: オプション（UI の並び順 = `FIELD_ORDER`）
- `rvc/realtime/core.py`: 窓の配置（trim / 先読み）、stateful 入力、aligned ゲイン、
  `algorithmic_delay_ms`
- `rvc/realtime/pipeline.py`: `configure_stream`、Protect の有声判定、
  時刻固定の状態（ノイズ、位相、F0 キャッシュ）
- `rvc/realtime/synthesis.py`: trim 用の生成呼び出し（`Synthesizer.infer` と同じ計算で、
  最新部分だけを生成）
- `rvc/lib/algorithm/generators/apex_gan.py`: ノイズ包絡の固定参照値、
  与えられたノイズ・位相での生成（学習時の経路は変更なし）
- `rvc/realtime/resample.py`: stateful リサンプラ
- `rvc/realtime/io_processing.py`: 入力のハイパス、ゲートのフェード、レベル表示
- `rvc/realtime/ring_transport.py`, `rvc/realtime/ring_buffer.py`: ring 転送
- `rvc/realtime/stream_eval.py`, `tools/realtime_stream_eval.py`: オフライン A/B
- `tools/apex_noise_voiced_ratio.py`: 学習データの有声率
- テスト: `tests/test_realtime_options.py`, `tests/test_realtime_synthesis.py`,
  `tests/test_realtime_ring_transport.py`, `tests/test_realtime_io.py`
