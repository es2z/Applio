# 学習の進捗を報告する手順

ユーザーから学習の進み具合を聞かれたときに、何を実行して何を返すかをまとめたもの。
集計は `tools/training_status.py`（TensorBoard のログと `logs/<model>/` を読むだけ。学習には触れない）。

## コマンド

```
env\python.exe -X utf8 tools\training_status.py <run> [<run> ...] [--fine [N]]
```

- `-X utf8` は必須。付けないと、環境によっては日本語やログの読み込みで `cp932` のエラーになる。
- `<run>` は `logs/` 以下のフォルダ名。一意に決まるなら一部だけでよい（例: `kushinada-large_4`）。
  複数当たると候補を出して止まるので、そのときはより長い部分を指定する。
- 引数を増やすほど横に並ぶ。2 つ以上なら 1 つ目を基準にした差と、更新回数をそろえた比較も出る。
- `--fine [N]` は直近 N epoch（既定 150）を 10 epoch 刻みで、ばらつきと傾き付きで出す。

## ユーザーの発話 → やること

| 言われたこと | 実行 | 返すもの |
|---|---|---|
| 「現在の進捗」「進捗教えて」「現状は」 | `tools\training_status.py <学習中の run>` | 状態（epoch / 速度 / 残り時間 / lr / 出力済み）、推移の表、見立て |
| 「A と B を比べて」 | `tools\training_status.py <A> <B>` | 上に加えて、差の列と「更新回数をそろえた比較」 |
| 「良くなってる？」「悪化してない？」「止め時？」 | `tools\training_status.py <run> --fine` | 傾き（100 epoch あたり）とばらつき。1 点ずつの上下で判断しない |
| 「バッチを変えるタイミングは」 | `--fine` の傾き | mel の改善幅、G と D の差の広がり方 |
| 「聴いて確かめたい」 | 変換コマンドを案内（下記） | 出力済みモデルのパスと手順 |

長い出力を `head` や `tail` で切ると、状態の行か表のどちらかが欠ける。両方必要なら切らずに出す。

## 出力の読み方

| 指標 | 意味 | 見方 |
|---|---|---|
| `mel` | 録音の潜在表現から音を作り直す誤差 | 主指標。embedder の違いはほぼ出ない |
| `kl` | 特徴量とピッチから潜在表現をどれだけ当てられるか | **embedder との相性が一番出る**。変換の質に効く |
| `fm` | 判別器の中間特徴の差 | 学習が進むと上がっていくのが普通（過去の学習でも 2 → 9〜11） |
| `g_adv` / `d_adv` | G と D の勝ち負け | 差が開き続けると D が勝ちすぎの方向。値そのものより傾きを見る |

**vocoder が違う学習どうしで `mel` と `fm` を比べてはいけない。** `train.py` は RefineGAN と
SiFi-GAN にはマルチスケール mel 損失（さらに 3.0 で割る）を、HiFi-GAN にはシングルスケールを使う。
表示は同じ `loss_avg_50/g/mel` でも中身が別の関数なので、大小に意味がない。`fm` も判別器の版
（HiFi-GAN は v2、RefineGAN / SiFi-GAN は v3）が違うと比較できない。

- **`kl` は比較できる**。vocoder に依らず `kl_loss × c_kl` で、`c_kl` は全 config で 1.0。
- `mel` を跨いで比べたいときは、両方のモデルを読み込んで**同じクリップに同じ指標**を当てる。
  1 ステップも回さずに測れる（`logs/<run>/filelist.txt` の特徴量をそのまま流し、出力と正解の
  mel L1 を取る）。これは warm start が効いているかの判定にも使える唯一まともな道具でもある。
- **どちらの経路で流すかで順位が変わる。必ず経路を明記すること**（下の実例2）。
  - **posterior パス**: 正解スペクトルを `enc_q` に入れて `dec` に流す。ボコーダ単体の再合成能力。
  - **推論パス**: `infer()`（`enc_p` → `flow` → `dec`）。実際に聴こえる音。用途としてはこちらが本命。

実例1（2026-09-16 測定、**posterior パス**）: `test1`(HiFi-GAN, 2280e) と
`refine-gan_..._4`(RefineGAN, 1280e) は `loss/g/mel` では 15.71 対 18.58 で前者が良く見えるが、
同じクリップに同じ mel L1 を当てると **1.561 対 1.517 で後者が良い**
（16 クリップの対応比較で差 +0.044±0.019、有意）。`kl` も 0.79 対 0.45 で後者が良い。
損失の表示だけを見ると結論が逆になる。

実例2（2026-09-17 測定、24 クリップ、対応比較）: **同じ 3 モデルでも経路を変えると順位が入れ替わる。**

| モデル | posterior mel L1 | 推論 mel L1 |
|---|---|---|
| `sifi_rvc_1024_kushinada2`(SiFi-GAN, 580e) | 1.4135 ±0.0342 | 0.3942 ±0.0075 |
| `test1`(HiFi-GAN, 2280e) | 1.3851 ±0.0288 | **0.3860 ±0.0091** |
| `refine-gan_..._4`(RefineGAN, 1430e) | **1.3431 ±0.0310** | 0.4449 ±0.0078 |

posterior では RefineGAN が最良（対 test1 で +0.0420±0.0112, t=3.74、有意）なのに、
**推論パスでは RefineGAN が最下位**（対 test1 で −0.0589±0.0049, t=−12.05、有意）。
つまり実例1 の「_4 の方が良い」は posterior 限定の結論で、実際に聴く経路では逆。
ボコーダ単体は良くても `enc_p`→`flow` から復元する経路が弱い、という形があり得る。
**聴感の判断材料にするなら推論パスで測ること。**

判断の目安（このデータセット・RefineGAN 48k での実績）:

- mel の改善が **100 epoch あたり 0.1 未満**が続いたら、条件を変えるか止めるかを考える頃合い。
- mel の 50 step 平均は **±0.15 程度ばらつく**。20 epoch 刻みの表で 1 点ずつ比べると、この幅を変化と読み違える。
  怪しいと思ったら必ず `--fine` で傾きを見る（実際に一度読み違えた）。
- 学習済み HiFi-GAN（`naru_20260906_kushinada_hubert_large_test1`）の `loss/g/mel` は、
  エクスポートが残っている信頼できる区間（〜2280e）で **15.7 ±0.27**、`kl` は 0.79。
  ただし**これは HiFi-GAN のシングルスケール mel なので、RefineGAN / SiFi-GAN の学習の
  数値と直接比べてはいけない**（上記）。到達目標として使うなら同じ vocoder の学習に対してのみ。
- 数値が頭打ちでも過学習は数値に出ない。最後は学習に使っていない音声で聴き比べて決める。

## 落とし穴

- **epoch と step は別物**。バッチサイズが違う学習を epoch で比べると、更新回数が違う。`--fine` ではなく
  「matched optimizer steps」の節を使う。
- **バッチを下げると、このカードでは時間あたりの進みが落ちる。** `refine-gan_..._4` で 6 → 4 に
  下げた前後の実測（2026-09-16）: 1 ステップの所要時間は 213 → 208 ms とほぼ変わらず、
  steps/epoch が 211 → 313 に増えた分だけ **1 epoch が 45 秒 → 65 秒（+44%）**。
  mel の改善は更新 1000 回あたり 0.0044 → 0.0033（更新あたり 25% 悪化）、epoch あたりは
  ほぼ同等、**時間あたりでは 0.074 → 0.057（−23%）**。変更直後に mel が 18.42 → 18.73 と悪化し、
  130 epoch 経っても変更前の自己ベスト 18.42 に戻っていない。
  1 ステップの時間が変わらない＝その範囲では GPU が飽和していないので、バッチを下げても
  速くならず、勾配が粗くなる分だけ損になる。VRAM が許すなら大きい方を維持する。
- **再開すると TensorBoard の step が飛ぶ**。`global_step` が「epoch × 1 epoch あたりの step 数」で
  数え直されるため。バッチを変えた学習ほど読みにくい。
- **フォルダをコピーした学習**は `eval/` に前のログが混ざることがある。ツールが注意を出す
  （例: `naru_dekai_20260915_kushinada_hubert_large_2`）。
- **停止中の学習はバッチサイズが分からない**（実行中のプロセスからしか取れない）。
- **再開では学習率を変えられない**。`config.json` を変えても、optimizer の状態から復元される。
  変えたい場合は別フォルダで warm start するか、再開時に上書きする仕組みを実装する。
- **GPU を使う重い評価（再合成の誤差など）は、先に確認を取ってから**。学習と GPU を取り合う。

## 聴き比べの案内

```
env\python.exe -X utf8 core.py infer ^
  --input_path <学習に使っていない音声.wav> ^
  --output_path <出力.wav> ^
  --pth_path logs\<run>\<run>_<N>e_<M>s.pth ^
  --index_path logs\<run>\<run>.index ^
  --f0_method mangio-crepe-full-speech ^
  --embedder_model <その学習の embedder>
```

- `--embedder_model` は既定が contentvec なので必ず指定する。学習に使ったものは
  `logs/<run>/model_info.json` の `embedder_model`。間違えると別物の音になる。
- TensorBoard の試聴音声（AUDIO タブ）は学習データからランダムに選ばれるので、聴き比べには使えない。
