# FCN-929 / FCN-929-RVC

FCN-993（[docs/fcn-993.md](fcn-993.md)）と同じ上流repositoryにある、
もう一つのFCNモデル **FCN_929** の移植です。実装・設定JSON・realtime・学習抽出の仕組みは
FCN-993と共通なので、ここではFCN-929で**異なる点**だけを説明します。
使い方や各JSON項目の意味は、FCN-993のドキュメントを参照してください。

## まず使うには（JSONは不要）

1. アプリを再起動します。
2. Pitch extraction algorithmで **FCN-929-RVC** を選びます。
3. **FCN profile JSONの欄は空欄のまま**にします。
4. 通常どおり変換・抽出・realtime開始を実行します。学習抽出ではGPU番号を指定します。

対応するcheckpointにFCN-929-RVCの設定が保存されていればそれを使い、なければ
同梱の **Balanced v1（FCN-929用）** を自動で適用します。
**FCN-929** は原推定結果そのもので、V/UV判定を加えません（FCN-993と同じ位置づけです）。

FCN-993で学習したモデルをFCN-929で変換することもできます
（「FCN method differs from checkpoint」と表示されるだけです）。
ただし学習時と別のF0推定器を使うことになるので、最良の結果は学習時と同じ方式です。

## FCN-993との違い

上流 `models/FCN_929/core.py` から確認した構造です。

| | FCN-993 | FCN-929 |
|---|---|---|
| conv層 | 6層 `(256, 32, 32, 128, 256, 512)`、kernel幅は全て32 | 5層 `(256, 32, 128, 256, 512)`、kernel幅 `(32, 64, 64, 64, 64)` |
| max-pool | conv1〜3の後（計1/8） | conv1〜2の後（計1/4） |
| 受容野（8 kHz） | 993 samples | 929 samples |
| native frame間隔 | 8 samples = **1 ms** | 4 samples = **0.5 ms** |
| 入力のzero padding | 496 | 464 |
| sliding norm窓 | 994（奇数を+1） | 930（奇数を+1） |
| realtime holdback | 140〜150 ms | **130〜140 ms** |
| BN eps、classifier、486 bins、30〜1000 Hz、復号 | 同一 | 同一 |

10 ms gridへの変換は、どちらも「中心の−5 ms〜+5 ms」の窓を使います。
FCN-993では10 native frame、FCN-929では20 native frameです。

### `median_frames` はnative frame数

`median_frames` は**native frameの数**で指定します。
FCN-929の1 frameは0.5 msなので、同じ値でも時間幅はFCN-993の半分になります。

| 時間幅 | FCN-993 | FCN-929 |
|---|---|---|
| OFF | 0 | 0 |
| 約2.5〜3 ms | 3 | 5 |
| 約5 ms | 5 | 9（4.5 ms） |
| 約9 ms | 9 | 17（8.5 ms） |

FCN-929-RVCで指定できるのは **0 / 5 / 9 / 17** です。
FCN-993の値（3など）を指定するとエラーになります。

## 同梱設定：Balanced v1（FCN-929用）

ファイル：[rvc-929-balanced-v1.json](../rvc/lib/predictors/fcn/profiles/rvc-929-balanced-v1.json)

~~~json
{
  "method": "fcn-929-rvc",
  "version": 1,
  "enter_threshold": 0.6,
  "exit_threshold": 0.35,
  "median_frames": 9,
  "coarse_min": 50.0,
  "coarse_max": 1680.0,
  "calibrated": false,
  "compile_model": false,
  "compile_mode": "default"
}
~~~

`coarse_min` / `coarse_max` はモデルの範囲設定で上書きされます（下の「coarse範囲」）。

- 有声化開始：confidence **0.60以上**（FCN-993は0.50）
- 有声維持：confidence **0.35以上**（FCN-993は0.40）
- median：**9 native frames = 4.5 ms**（FCN-993の5 ms相当）

### この値を選んだ根拠

FCN-993のBalanced v1を決めたときと同じ、上流付属のmanual例4／5／11／28
（10 ms単位で計1,283 frames、参照有声804、参照無声479）で比較しました。
各セルは「無声を有声とした数 / 有声を無声とした数」です。

| enter＼exit | 0.35 | 0.40 | 0.45 | 0.50 |
|---|---|---|---|---|
| 0.50 | 82 / 24 | 72 / 25 | 62 / 32 | 54 / 40 |
| 0.55 | 70 / 28 | 58 / 29 | 50 / 36 | 43 / 44 |
| **0.60** | **58 / 28** | 50 / 29 | 42 / 37 | 36 / 46 |
| 0.65 | 49 / 33 | 41 / 34 | 34 / 41 | 28 / 51 |

参考：FCN-993-RVC（0.50／0.40）は66 / 20、Mangio-CREPE-full-speechは83 / 18です。

- FCN-993と同じ0.50／0.40だと、FCN-929は無声の誤有声化がFCN-993より多くなります（72 vs 66）。
  FCN-929のconfidenceは、無声区間でやや高めに出る傾向があります。
- 「FCN-993-RVCの誤有声化（66）を超えない範囲で、有声の取りこぼしを最小にする」という基準で
  **0.60／0.35**（58 / 28）を選びました。
- 0.60／0.40（50 / 29）も候補でした。ただし実音声3本でRMVPEの有声区間と比べると、
  0.35のほうが取りこぼしが同じか少なかったため（下表）、声を残す側を優先しました。
  これはFCN-993の標準値を決めたときと同じ方針です。

実音声でRMVPEの判定と比較した結果（RMVPEは正解ではなく、比較用の基準です）：

| 音声 | 設定 | RMVPE有声のうち落とした割合 | RMVPE無声のうち有声にした割合 |
|---|---|---:|---:|
| reference.wav（35 s） | FCN-993-RVC 0.50／0.40 | 8.5% | 13.2% |
| | FCN-929-RVC 0.60／0.40 | 13.2% | 7.1% |
| | **FCN-929-RVC 0.60／0.35** | **11.6%** | **8.3%** |
| aaaaa.wav | FCN-993-RVC 0.50／0.40 | 6.6% | 35.0% |
| | **FCN-929-RVC 0.60／0.35** | **6.2%** | **17.5%** |
| cccc.wav | FCN-993-RVC 0.50／0.40 | 2.4% | 26.3% |
| | **FCN-929-RVC 0.60／0.35** | **2.8%** | **7.9%** |

reference.wavでは、FCN-929-RVCはFCN-993-RVCより声を多めに落とします。
語尾や弱声が切れると感じたら、exit_thresholdを0.35→0.30へ下げてください
（調整の方向はFCN-993のドキュメントと同じです）。

ピッチの精度は、manual 4例の両者有声frameでFCN-993とほぼ同等かやや良好です
（50 cent超のずれ：FCN-929 約6.1%、FCN-993 約7.1%）。

**適用範囲**：4例は開発用の小標本で、話者分離した独立テストではありません。
聴感評価もしていないため、`calibrated` は `false` のままです。
比較結果は[fcn-929-rvc-default-evaluation.json](fcn-929-rvc-default-evaluation.json)にあり、
次のコマンドで再現できます：

~~~powershell
.\env\python.exe -X utf8 tools/evaluate_fcn_rvc_presets.py <FCN-f0> --method fcn-929-rvc --output docs/fcn-929-rvc-default-evaluation.json
~~~

## coarse範囲（FCNの既定は1000 Hz）

ピッチ埋め込みの量子化範囲は、学習抽出の「F0 Coarse Range」（CLI：`--f0_coarse_max`）で
モデルごとに決まります。FCN（FCN-993／FCN-929系）では **750 / 1000 / 1100 / 1680** を選べ、
**既定は1000（推奨）** です。750と1000はFCN専用で、ほかの方式は1100 / 1680（既定1680）です。

- FCNの出力binは30〜1000 Hzで終わるので、1000より上のbinはFCNの推定では使われません。
- 調和音で測ると、FCNが正確なのは750 Hz前後までで、それを超えると790〜810 Hz付近に張り付きます。
  RMVPEとFCNF0++は1100 Hzまで正確でした。

倍音を含む合成音（1/k振幅、7倍音まで）の中央値（Hz）。推論と同じ `Pipeline.get_f0` 経由で、
F0探索範囲はモデル既定の50–1680 Hz、mangio-crepeのデコーダーはviterbiです（2026-09-29）。

| 方式 | 600 | 700 | 750 | 800 | 900 | 1000 | 1100 | 1250 | 1400 |

| rmvpe | 600.5 | 699.8 | 751.9 | 800.8 | 901.4 | 1003.6 | 1100.2 | 1251.8 | 699.1 |
| hpa-rmvpe-76000 | 599.6 | 699.6 | 749.7 | 799.1 | 900.0 | 1000.6 | 1099.6 | 1250.2 | 1400.1 |
| hpa-rmvpe-76000-aligned | 599.6 | 699.6 | 749.7 | 799.2 | 900.1 | 1000.6 | 1099.6 | 1250.3 | 1400.0 |
| hpa-rmvpe-112000 | 599.5 | 699.7 | 750.0 | 799.7 | 900.2 | 999.7 | 1100.5 | 1250.1 | 1397.2 |
| hpa-rmvpe-112000-aligned | 599.5 | 699.7 | 750.2 | 799.8 | 900.2 | 999.7 | 1100.6 | 1250.2 | 1397.1 |
| crepe-full | 601.9 | 698.5 | 742.0 | 796.9 | 896.3 | 992.1 | 1100.7 | 1247.2 | 1400.5 |
| mangio-crepe-full | 603.8 | 700.6 | 743.5 | 796.2 | 893.5 | 990.4 | 1100.6 | 1251.1 | 1400.1 |

- FCNは750 Hzまで、speechの2種は800 Hzまで正確で、それより上では半分の高さなどの誤りになります。
- RMVPEは1250 Hzまで、HPA-RMVPE全4種とcrepe-full／mangio-crepe-fullは1400 Hzまで追えます。
- crepe系の1100 Hz超は、F0探索範囲がモデルのcoarse範囲（ここでは1680）に従うようになったので出る値です。
  以前の通常推論は1100 Hzで打ち切っていました。

750を選ぶと、それより高い音（高い声や、変換時にキーを上げた場合）はcoarseの最上位binに張り付きます。
デコーダーに渡る連続値のF0（pitchf）は正確なままで、影響するのはピッチ埋め込みだけです。
1000と750のどちらが良い音になるかは測っていません。

## 実音声での動作

`tools/compare_f0_methods.py` で、RMVPEを基準に比較しました
（med c＝両者有声frameでのcent差の中央値、lag＝RMVPEに対する時刻ずれ）。

| 音声 | 方式 | 有声率 | V/UV切替 | 穴 | spike | med c | lag |
|---|---|---:|---:|---:|---:|---:|---:|
| reference.wav | FCN-929-RVC | 62.3% | 206 | 5 | 1 | 9.1 | +3 ms |
| | FCN-993-RVC | 66.0% | 262 | 27 | 18 | 10.6 | +3 ms |
| | RMVPE | 67.4% | 126 | 2 | 0 | - | - |
| cccc.wav | FCN-929-RVC | 83.6% | 8 | 0 | 0 | 3.5 | 0 ms |
| | FCN-993-RVC | 86.8% | 12 | 1 | 1 | 4.0 | +1 ms |
| | RMVPE | 84.8% | 8 | 0 | 0 | - | - |

- 時刻ずれは±3 ms以内で、FCNF0++やHPA-RMVPEのような補正（aligned版）は不要です。
- FCN-993-RVCに比べて、V/UVの切替、1 frameの穴、spikeが少なくなっています。
- 原推定のFCN-929（V/UV判定なし）も、RMVPEとの差の中央値は3.5〜9.9 centでした。

## Realtime

FCN-993と同じ `FCNStream` と `FCNRealtimeSession` を使います。holdbackは次のとおりです。

- baseline（FCN-929）、またはmedian 0：**130 ms**
- median 5〜17（Balanced v1を含む）：**140 ms**

受容野と正規化窓がFCN-993より短いため、上限がFCN-993より10 ms短くなります。
いずれもcapture filtering約0.46 msと、最大10 msのgrid alignmentが加わります。

実際の `VoiceChanger` での測定（reference.wavの先頭10秒、512 msブロック、
FCN-993-RVCで学習したMRF HiFi-GAN／kushinada-hubert-largeモデル）：

| 方式 | holdback | 処理時間（2ブロック目以降の中央値） | 最大 |
|---|---:|---:|---:|
| FCN-929-RVC | 140.46 ms | 55.7 ms | 182.7 ms ※ |
| FCN-929 | 130.46 ms | 53.4 ms | 72.9 ms |
| FCN-993-RVC | 140.46 ms | 52.6 ms | 67.3 ms |

※最初に実行した方式なので、embedderのTorchCompileのwarm-upが含まれています。
FCN-929はnative frameがFCN-993の2倍ありますが、層が1つ少なく、処理時間はほぼ同じです。
結果は `rvc/lib/predictors/fcn/smoke-929-realtime.json` にあります。

## CUDA検証結果（2026-09-28）

環境：RTX 4090、PyTorch 2.13.0+cu132。
参照：隔離環境のTensorFlow CPU 2.18.0／Keras 3.15.1、oneDNN OFF。
原HDF5を上流 `core.py` どおりに組んだConv2D/BNへ直接読み込んで比較しました。
oracleの層構成は移植側のコードからimportせず、上流から書き写しています。

| 測定 | 結果 |
| --- | --- |
| float64、929／1000／1001／8001／16001 samples | 全層が1e-9基準で合格。最大差 約9.7e-13、復号差 最大3.6e-12 cent |
| float32、同じ長さ | 最終activationが atol 1e-5 / rtol 1e-4 で合格。最大差3.4e-6、復号差 最大0.0011 cent |
| 16 kHz全経路、7波形（正弦、倍音、noise、impulse、DC、silence、微小振幅） | 全波形で合格。最大activation差1.06e-6、最大pitch差0.00115 cent |
| CUDAとCPU（NumPy経路）の一致 | 有声判定の不一致0、pitch差0.0012 cent以下 |
| streamingとofflineの一致 | 冒頭以降でpitch差0.0001 Hz以下 |
| 学習抽出 | 初回抽出、同一設定の再実行は再利用、993／929の切替で再抽出 |
| `core.py infer` | 実モデル（FCN-993-RVCで学習したMRF HiFi-GAN／kushinada）で変換成功 |
| realtime `VoiceChanger` | 実モデル・実音声で19ブロック変換成功、holdbackは計算値どおり |

float32では、FCN-993と同じく一部の中間層が1e-5基準を超えます（最大3.8e-4、conv5）。
float64では全層が一致するので、これはlayoutやarchitectureの誤りではなく、FP32の丸め差です。
FCN-993と同じく、float64で全層を確認したうえで `--output-gate` を使っています。

reportは `rvc/lib/predictors/fcn/parity-929-*.json` にあります。

## Weight・出典・license

配置先は `rvc/models/predictors/fcn-929.pt` です。
隣の `fcn-929.manifest.json` も、読み込み時に必要です。
どちらもFCN-993と同じく `.gitignore` の対象です。

- 原repository：<https://github.com/ardaillon/FCN-f0>
- 固定commit：8a2b530af821319b6badca93c8a0ed1f14bfee3c
- 原HDF5 `models/FCN_929/weights.h5` のSHA-256：34bc883250f68c28272c0667e18a730cc92ef7074d7497d101f25adae218fc4e
- 変換後 `fcn-929.pt` のSHA-256：e05f2cdc22762decaf50e3024beb6e0e785c67037c0cfd6219080bb7e23185cd

HDF5の32個のfloat32 parameterを、名前・shape・有限値で検証してから変換します
（FCN-993より1層少ないため、parameter数も6個少なくなります）。

~~~powershell
.\env\python.exe tools/convert_fcn993.py --architecture fcn-929 <FCN-f0>/models/FCN_929/weights.h5 rvc/models/predictors/fcn-929.pt
~~~

変換と検証に使うh5py／TensorFlowは `tools/requirements-fcn-validation.txt` を参照し、
隔離環境へ導入してください。変換スクリプトはtorchとresampyもimportするので、
その環境には両方が必要です。アプリの実行時にTensorFlowやh5pyは不要です。

TensorFlowとの照合手順（`--architecture fcn-929` を付ける以外はFCN-993と同じ）：

~~~powershell
# TF環境
python tools/validate_fcn993.py oracle --architecture fcn-929 weights.h5 inputs.npy oracle.npz
python tools/validate_fcn993.py preprocess --architecture fcn-929 waves16k.npy wave-inputs.npy
# アプリ環境
.\env\python.exe tools/validate_fcn993.py compare --architecture fcn-929 --device cuda fcn-929.pt inputs.npy oracle.npz
.\env\python.exe tools/validate_fcn993.py waveform --architecture fcn-929 fcn-929.pt waves16k.npy wave-oracle.npz
~~~
