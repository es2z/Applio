# リアルタイム変換: 次の候補（2026-11-10）

ローカルの Claude Code 向けのメモです。前提は `docs/HANDOFF-realtime-latency-quality.md` と
`docs/realtime-latency-quality.md`。ここにあるのは**案**で、どれも未実装・未検証です。
やるかどうか、どう作るかは、実機と音を確認できる側で判断してください。
方針は従来どおり（オプトイン、初期値 = 従来の動作、音色は耳で決める）。

## 現状（ユーザーから）

- trim + ring を使用。Chunk 1280 ms で実遅延は約 1.7 s。
- Chunk を縮めると（trim / ring でも）音への影響が大きい、という実感がある。
- Index は SPIN 追加学習済みの embedder で抽出した特徴量から作っている。
  リアルタイム時にどの embedder を選んでいるかは未確認（下の B に関係する）。
- データセット（KU100 バイノーラル）は、近い耳のチャンネルを発話単位に近い形で選択済み。
  ささやき・息は手動で除外済み。吹かれ・ポップは聴いた限り無い。

## A. Chunk を縮めたときの劣化（遅延を下げる本筋）

遅延に乗るのは Chunk で、trim なら Extra（過去文脈）は乗らない。
Chunk を縮めると、次の「ブロックごとに 1 回決まるもの」の頻度と割合が上がる。

| | 1280 ms | 240 ms |
|---|---|---|
| クロスフェード中の割合（Crossfade 0.138 s のとき） | 11% | 58% |
| つなぎ目 | 0.8 回/秒 | 4.2 回/秒 |
| 未来を「Crossfade + 先読み」しか見ずに作られる音 | 各ブロックの末尾 | ほぼ全部 |

1. **まず既存オプションで切り分ける。** 同じ録音で `tools/realtime_stream_eval.py` を使い、
   Chunk 240〜480 ms（40 ms の倍数）で次を 1 つずつ足して聴く。
   - 時刻固定 3 種（`time_locked_noise` / `phase_continuity` / `f0_cache`）
   - `apex_noise_envelope = fixed`（短い生成区間では有声率がブロックごとにばらつく）
   - `gain_mode = aligned`
   - `lookahead_s` 0 / 0.05 / 0.1、Extra 2.0〜2.5 s
   ユーザーのテンプレートの `experimentTab` を見て、どれが未使用かを先に確認すること。
2. **未来文脈の必要量を測るツール（未実装）。** 先読み 0〜300 ms について、窓の最新端の
   embedder 特徴量と F0 が、全文脈で計算した値からどれだけずれるかを出す。
   これで 3 をやる価値があるかが決まる（150 ms で十分近いなら、原因は 1 の側）。
3. **リアルタイム条件の特徴量で微調整（未実装、S8 / T7）。** 抽出時にリアルタイムと同じ窓を
   滑らせ、「再生される位置」の特徴量を集めて、今の G/D から続けて学習する。
   - embedder の特徴量だけ。F0 は全文脈のままにする（精度の落ちた F0 で学習すると、
     モデルが F0 に従わなくなる方向に働く）。
   - 未来文脈の長さは乱数で振る（特定の Chunk 設定専用にしない）。
   - 抽出条件は `model_info.json` の抽出仕様に記録し、既存の特徴量と混ざらないようにする。
   - 未来を見ないと決まらない情報は戻らない。全文脈と同等にはならない見込み。

## B. Index

- `index_search = exact` / `index_top_k`（実装済み、865b13c）。GPU・実 Index では未計測。
  `tools/index_recall.py` で、従来の検索（nprobe 1）の取りこぼしを自分の Index で測れる。
- **検索に使う特徴量を SPIN に揃える（未実装）。** リアルタイムの embedder が元の kushinada で、
  Index が SPIN 特徴量なら、検索する側と Index 側で空間がずれている。SPIN 版は 20 層目まで
  元と共通なので、追加は 2 層分。検索は SPIN、返す値は「SPIN のまま」と「同じフレームの
  元の特徴量」の両方を試せる形が望ましい（今ユーザーが良いと感じているのは前者の値）。
  リアルタイムの embedder が SPIN 版なら、この項目は不要。

## C. データセット

どちらも「レポートを出すだけ、音は変えない」ツールにする。

1. **損失による外れ値探し（優先）。** 学習済み G で、クリップごとの mel 損失
   （posterior 経路、シード固定）を全クリップについて出し、上位 3〜5% を聴いて判断する。
   `rvc/train/evaluation.py` の計算を流用できる見込み（未確認）。
   損失が高い = 悪いデータ、ではない（笑い声や高い声も上位に来る）。自動では消さない。
2. **録音位置の分布。** 元のステレオで、クリップごとの左右のレベル差（帯域別）と時間差を出す。
   両耳は同じ声を聞いているので、内容の影響が打ち消されて位置だけが残る
   （片チャンネルのスペクトルは、内容と声の強さでも大きく変わるので不向き）。
   分布が 1 つに固まっていれば何もしない。分かれていれば、少数側の除外か、
   位置ごとに別の話者 ID を付けて学習する。元のステレオファイルが必要。

## 進める順の目安

A-1（設定だけ）→ C-1 → A-2 → その結果で A-3 → C-2。B は embedder の確認が取れてから。
